# Contamination Protocol

**Status:** DRAFT protocol from overnight Session E, for Tianle to approve. It's worth 20 of the 100 points ("evaluation rigor and contamination control") and is the part of the write-up most likely to be questioned.
**Brief's wording:** "Keep evaluation data separate from anything that touched training, **including the prompts used to generate it**." And: "We will build a hidden set to your published schema with a different process."
**Implementation hooks:** `step6_evaluation/split_guard.py` (Session F) does hashing, freezing and overlap checks; `step1_data_generation/` (Session A) does seeded sampling; `step6_evaluation/` (Session C) does scoring. This doc says **what** must hold; those modules enforce it.

---

## 1. Threat model: how our numbers could be inflated

| # | Leak path | Example | Control (section) |
|---|---|---|---|
| L1 | Eval cases in training data | An eval packet (or its teacher output) ends up in an SFT file | §2 splits, §5 overlap checks, §6 teacher isolation |
| L2 | Near-duplicates | Same truth, different layout; or same applicant name and list entry in train and eval | §3 entity partitioning, §5 MinHash and entity checks |
| L3 | Shared generation recipe | Eval made with the same config and prompts as train, so we test template memorization | §4 separate configs and prompts; the OOD set |
| L4 | Tuning on the test set | "Best prompt" or the checkpoint chosen by eval score | §7 dev set and the eval-look budget |
| L5 | Label leakage via the truth object | Truth fields (tags, `reality`) accidentally rendered into packets | §8 render guards |
| L6 | Silent mutation of frozen eval | Regenerated eval differs from the one reported | §5 hashing and freezing |
| L7 | Teachers seeing eval cases | Teacher outputs on eval cases reused as training data | §6 |

## 2. Splits

| Split | Size | Config | Seed range | Used for | Never used for |
|---|---|---|---|---|---|
| `train` | 3,000 (+ ~1,000 twins, + mined hard cases) | `configs/train.yaml` | 1,000,000–1,999,999 | Teacher calls, SFT, DPO, mining | Reporting |
| `dev` | 150 | `configs/train.yaml` (same distribution as train) | 2,000,000–2,099,999 | Prompt iteration, checkpoint selection, label pilot (`data_design.md` §6), teacher choice | Training; reporting |
| `eval_id` | 300 | `configs/eval_id.yaml` (same **method**, different config file, quotas) | 3,000,000–3,099,999 | Table 1 / Table 2 | Anything before the final run of each row |
| `eval_ood` | 150 | `configs/eval_ood.yaml` + LLM renderer / hand templates | 4,000,000–4,099,999 | Table 1 / Table 2 (reported separately and combined) | Same as above |
| `pilot` (throwaway) | as needed | any | 9,000,000+ | Debugging the generator | Everything else; deleted before freeze |

**Why dev uses the train config:** it measures what selection needs to measure (in-distribution quality) without touching eval configs. Eval-ID uses a *different config file* (stratified quotas, held-out layouts L7–L8, eval-partition pools), even though it's generated by the same code. That's honest "in-distribution, different draw." **Eval-OOD is the one that answers L3.**

**Seed discipline.** Seeds are disjoint integer ranges by split, and the generator **asserts** that the seed falls in its split's range. A case's `case_id` embeds its split (`eid-000123`, `ood-000045`), so a stray eval case in a training file is detectable by id alone.

## 3. Entity partitioning (the near-duplicate leak specific to KYC)

A model can "memorize" a fictional sanctioned person: if "Rustam KHAIDAROV, a.k.a. Roustam Khaydarov" is a true match in training, then an eval case with the same list entry is partly answered by memory, not by matching skill.

**Rule:** every reusable entity pool is partitioned **by stable hash** into a train part and an eval part, and each split draws only from its own part:
- fictional given and family names (per script), and their transliteration variant sets;
- watchlist entries (primary name + aliases + DOB + nationality), PEP positions, adverse-media stories;
- fictional streets, cities' street lists, PoA issuers;
- **injection texts** (the pool of model-directed instructions; eval injections are written separately so the model can't learn the literal strings);
- document-number ranges.

Partition by `sha256(pool_name + item) mod 10`: 0–6 → train, 7 → dev, 8–9 → eval. Rules, scripts, and countries are **shared** across splits by design; we test *skill on new instances*, not new *rules*. (The two OOD-only countries are the exception and deliberately test format transfer.)

## 4. Separate configs and prompts

- Eval configs (`configs/eval_*.yaml`) are written **after** the train config and **not** derived by copy-editing it. They differ in mix weights, quotas, layouts and pools. Their hashes are frozen together with the data.
- **Generation prompts:** the OOD renderer prompts (`step0_rules/prompts/eval_ood/`) are written fresh, and no train-side generation prompt is derived from them. Train-side LLM generation (if any is added later, e.g. LLM-paraphrased training packets for robustness) uses `step0_rules/prompts/train/`, written independently and **checked against the eval prompts for n-gram overlap** (§5).
- **The task prompt (system prompt) is not a generation prompt.** The same task prompt is used for training, dev and eval inference. That's correct and expected, because it's the instruction the deployed model gets. State this explicitly in the write-up so nobody reads it as leakage.
- **Teacher prompts** (what we send teachers to produce training targets) are task prompts plus at most policy text, never eval-config content.

## 5. Hashing, freezing and overlap checks

**Freezing (Saturday ~14:00, after the label pilot):**
1. Write `data/eval/MANIFEST.json`: for every eval file, its sha256, number of rows, generator git commit, config sha256, seed range, and the renderer model IDs and prompt hashes for OOD.
2. Commit the manifest; tag the commit `eval-freeze-v1.0`. (The eval JSONL itself is committed too. It's synthetic, and a reproducible eval needs it.)
3. `python -m step6_evaluation.split_guard verify-freeze` recomputes the hashes. **The eval harness refuses to run if the hashes don't match the manifest** (Session C/F wiring). Every Table 1 row records the manifest hash it ran against.
4. The "regenerate the evaluation set" command (a brief requirement) regenerates from config + seeds and **must reproduce the frozen hashes byte for byte** for eval-ID and O2. O1 (LLM-rendered) can't be byte-reproducible from the API, so the command replays **cached renderer responses** and documents that.

**Overlap checks** (`split_guard check`, run on **every** file under `data/train*` before any training job; exit non-zero on failure):

| Check | Method | Threshold (fail) | Catches |
|---|---|---|---|
| Exact case | `case_id` prefix and sha256 of the packet | any hit | L1 |
| Normalized exact | lowercase, strip whitespace and punctuation, then sha256 | any hit | L1 with formatting changes |
| Truth-level | hash of canonicalized truth (excluding seed and layout) | any hit | Same facts, different render (L2) |
| Near-duplicate | MinHash (128 perms) over word 5-gram shingles; LSH | Jaccard ≥ 0.80 → fail; 0.60–0.80 → report | L2 |
| Long n-gram | Any shared 13-gram (word level) outside an allowlist of boilerplate (section headers, T&C footers) | Report the count; fail if >1% of eval cases are affected | L2, L3 |
| Entity | Names, list entries, document numbers, injection strings in eval vs the train pools | any hit | §3 violations |
| Prompt | 13-gram overlap between `step0_rules/prompts/eval_ood/*` and `step0_rules/prompts/train/*` | any non-boilerplate hit | L3 |

**Report** the numbers (e.g. "0 exact, 0 truth-level, 0 near-dup ≥0.8, max Jaccard 0.41, 0 entity collisions") in the write-up. Numbers are more convincing than "we checked."

**Sanity test of the checker:** deliberately inject 5 eval cases (one per check type) into a scratch train file and confirm `split_guard` catches every one. Save the output. This answers "how do you know your checker works?"

## 6. Teachers never see eval cases (and what that means precisely)

`CLAUDE.md` says teachers never see eval cases. But the brief requires frontier models (including our teachers, GPT and Gemini) to be **run on eval as baselines**. Both can hold if the rule is stated precisely. **PROPOSED wording for Tianle to approve:**

> No output from any model call on an eval or dev case is ever written into a training file. Teacher-data jobs read only from `data/train*`. Baseline jobs write only to `outputs/eval/`. Training jobs read only from `data/train*` and refuse any path containing `eval` or `dev`.

**Enforcement:**
- Path separation: `shared/frontier_api/batch.py` and the training scripts take a split argument and **assert** it's `train` for teacher and training jobs.
- `split_guard check` runs on the final training JSONL (it catches eval `case_id`s and packet hashes even if a path assertion is bypassed).
- Caches: the on-disk request cache (`shared/frontier_api/clients.py`) is keyed by request hash; eval-call caches live under `outputs/eval/cache/` and the training data builder never reads from there.
- **Provider side:** API traffic isn't used for provider training by default for OpenAI, Anthropic and Google paid tiers. **Verify each account's data-retention setting on Saturday** (Gemini's *free* tier may use data for training, so use the paid tier for eval calls). Even if a provider did train on our eval calls, that would affect the *teacher*, not our student, and couldn't reach our training data before Sunday.

## 7. Selection discipline: no tuning on the test set

- **Prompt iteration** ("best prompt" for every model) happens on **dev only**. Record each prompt version and its dev score; the eval run uses the final version, run **once**.
- **Checkpoint, hyperparameter and technique choices** use dev only.
- **Eval-look budget:** each Table 1 / Table 2 row is evaluated on eval **once**, after the choices for that row are fixed. Every eval run is logged (`outputs/eval/RUNLOG.jsonl`: time, model, prompt hash, manifest hash). Report the total number of eval runs in the write-up. If a bug forces a re-run, log why.
- **The final model choice** (which stage stack ships) is made on dev, and also reported on eval. If dev and eval disagree about the best stack, ship the dev choice and say so.
- **Label fixes after freeze** are by rule only and versioned (`data_design.md` §6 Stage C).

## 8. Render guards (truth → packet leaks)

- The renderer receives a **view** of the truth object with labels and meta fields removed (`reality`, `tags`, `ambiguity.flags`, `tamper.original`, `case_id`'s split prefix, `config_id`). A test asserts that none of these strings or enum values appear in any rendered packet.
- Packet ids shown in the packet are random per render (not the `case_id`), so the split is not visible to the model.
- Field names in the packet never use our schema's enum values verbatim where that would leak the answer (e.g. no "Disposition: false_positive" in vendor output; vendor fields say "Match strength: 82").

## 10. Defending each point under questioning

| Likely question | Answer (with the evidence to show) |
|---|---|
| "Isn't your eval just more of your training distribution?" | Eval-ID is, deliberately, and we label it in-distribution. Eval-OOD uses a different config, different seed range, entity pools disjoint by hash, two renderer methods (LLM free-form from two families + hand-written templates by a different author), and two unseen countries. We report both, and the gap between them. |
| "Did any eval case leak into training?" | `split_guard` ran on every training file: 0 exact, 0 truth-level, 0 near-dup ≥0.8 (max Jaccard X), 0 entity collisions. The checker caught all 5 planted leaks in its self-test (output in `reports/`). |
| "Your teachers are also baselines. Didn't they see eval?" | As baselines, yes, as the brief requires. No output from an eval or dev call ever enters a training file: path assertions + `split_guard` on the final JSONL. Provider data-retention settings were verified as no-training on [date]. |
| "How did you pick the 'best prompt'?" | On a 150-case dev set from the train config, N iterations, logged. Eval was run once per row; total eval runs = X (RUNLOG). |
| "How do you know your labels are right?" | Labels are computed by code from the truth object. Frontier-disagreement pilot: suspect-label rate went from X% to Y% after rule fixes; 20 hand checks, Z/20 agreed; N post-freeze label changes, versioned and disclosed. |
| "Could the student just memorize sanctioned names?" | Name, alias and list-entry pools are partitioned by hash; no eval entity appears in training (entity check = 0). |
| "Did the prompts used to generate eval touch training?" | The OOD renderer prompts are separate files with a 13-gram overlap check against train prompts (0 hits). The task prompt is shared by design: it's the deployed instruction, not a generation prompt. |
| "Can you reproduce the eval set?" | `make eval-data` regenerates eval-ID and O2 byte for byte (hashes match the manifest); O1 replays cached renderer outputs, because LLM APIs aren't deterministic. |
| "What would Zorbe's hidden set do to you?" | Our best estimate is the OOD column and the seen-vs-unseen-layout slice; if those are much lower than eval-ID, we say so in the write-up rather than headline eval-ID. |
